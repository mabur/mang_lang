ANSATZ
Lets' assume no-escape rule and late binding. What can we prepare in the semantics or refernce walking tree interpreter, to make it closer to a bytecode vm, or to make it easier to implement a bytecode vm?


IDEAS

The useful framing is that a bytecode VM is only the expression evaluator. Frames, values, closures, built-in calls, statements and errors are shared machinery, and all of it can be built and tested inside the tree walker first. When that is done, writing the VM is replacing one recursive function with a compiler and a dispatch loop. Here is what I would prepare, in the order I would do it.

Pin the semantics with tests first
No-escape rule. Add failing programs: a function factory, a closure returned inside a tuple and inside a dictionary, a closure put into a table owned by the caller. Pin the error message.
Late binding. Add the case from your last message, and one where a closure created before a loop is called inside the loop after the captured name has been reassigned.
Eager errors. Add programs with an error in a definition that the result never reads, and pin that they fail. Today they pass silently because errors are values.
Unassigned slots in reused blocks. A block inside a for loop with a name defined only in a skipped if. Decide reinitialize versus static error and pin it.
These tests protect the refactors below and become the VM's acceptance suite.

Refactor the tree walker toward the VM's data model

* Separate storing of statements and definitions for DictionaryExpressions and DictionaryValues
* Make the linear seach lookup faster for child@dictionary and function argument lookup in (a b) out a and in {a b} out a

3. Split the dictionary slot from the definition. A dictionary value is today a range into the shared definitions array, where each entry carries a name and a value. Change it to point at the static name list of the expression it was built from, plus a range of plain values. Names stay available for child lookup, dictionary-argument functions and the dictionary type check, which all search by name at runtime. Values become 16 bytes with no name beside them, which is what a frame slot must look like. The `Definition` struct then serves only the parsed statement and can take the statement suffix. The tests cover every use of this.

4. Pin the behavior the frame work can break. Add tests that already pass: late binding, with a name reassigned between two calls of a closure that reads it, and a closure created before a loop and called inside it. Add a block inside a for loop with a name defined only in a skipped `if`, pinning that the second iteration sees the any-value again. These are the cases where reusing slots would silently change results.

5. Frame layout in the resolver, computed beside the old addressing. The resolver today produces steps to parent counting every scope. Have it also produce environment depth plus slot offset, where an environment is a function frame or a value-position dictionary, and frame-position blocks, meaning argument frames and the operand of an immediate `name@`, are flattened into slot ranges of the enclosing frame. Each function records its frame size. Each for statement reserves one extra anonymous slot for the remaining container. Keep the old fields, and assert at every lookup that both addressings find the same slot. This is the VM's addressing mode and the resolver output becomes its symbol table.

6. The frame stack and the two environment kinds. Introduce a frame array with a small header holding the static link and a serial. Function application pushes a frame, frame-position blocks reinitialize and write their slot range, value-position dictionaries construct in the arena as now with their static link pointing at the enclosing frame. Lookup dispatches on the environment kind, so a frame is one more case beside the arena dictionary. A function value records the nearest stack frame in its chain and that frame's serial, and calls compare them. The for loop uses its hidden slot, so the iterator object and the implicit take in variable lookup disappear here. The type checker calls the same application code and gets the frames for free. Switch the evaluator to the new addressing, remove the old fields, and add the no-escape tests: a function factory, a closure returned inside a tuple and a dictionary, and one stored into a caller's table, all failing with the "used after the call that created it ended" message. This is the big speed win and where the thousand tests earn their keep.

7. Direct arities for built-ins. Every built-in takes one value and the binary ones unpack a tuple, so `add!(x y)` allocates a tuple on every call, as do the `+=` and `--` statements through the two-element tuple helper. Add a two-value entry point per binary built-in, and a node variant for a built-in applied to a literal tuple that evaluates the children and calls it directly. That node is the future add instruction and the built-in table becomes the VM's native function table.
